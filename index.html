Technical Details — AIChE Chem-E-Car

Contribution across subsystems

Contributed to chemical preparation, integration, testing, troubleshooting, and safe operation across the team’s propulsion and stopping systems.

Electrochemical propulsion

A custom alkaline zinc battery used approximately 2 M NaOH electrolyte. A small amount of H₂O₂ increased oxygen availability. Zinc oxidation and zinc-air chemistry supplied power to a DC motor.

Battery output
Approx. 6 V · 0.4–0.8 A
Motor
Approx. 3–6 V DC
Gross vehicle mass
Approx. 4.6 kg
Average measured velocity
Approx. 0.3 m/s
Expected conditions
Approx. 26 °C · 1 atm

Reaction-based timing

Fuchsin dye reacted with excess NaOH, with approximately pseudo-first-order behavior under those conditions. A photometer continuously measured the color change as the dye faded. Arduino read the optical signal and cut motor power at a predetermined threshold, allowing the chemical reaction to function as the timing mechanism.

Experimental practice

Reaction kinetics, electrochemistry, optical sensing, Arduino control, and system integration were combined with chemical handling, waste disposal, PPE, and laboratory procedures.

Real-time systems / architectureP—04

SoundBoy

An independently built real-time audio processing & control system: multiple streams, modular local ML processing, and failure-aware operation on Apple Silicon.

~165 ms p95 processing time per 500 ms RVC input interval

View SoundBoy release ↗ (opens in a new tab)
SwiftPythonCore AudioPyTorch
Technical Details — SoundBoy

System architecture

Acquires multiple continuous audio streams, then processes, transforms, mixes, and routes them through modular processing units. Independent source controls, source isolation, adjustable processing variables, bounded buffers, and persistent application/system state support operation.

Modular interfaces

Native hardware interfaces communicate with local machine-learning and voice-conversion processing through a versioned interprocess protocol. Processing engines can be replaced without redesigning the control application.

Resources and failure handling

  • Overload detection, device-change recovery, failure-safe shutdown behavior, and automatic resource cleanup.
  • Persistent processing workers; expensive models loaded only when needed, with one voice-conversion model active at a time.
  • Avoids unnecessary disk writes.

Performance validation

Measured approximately 165 ms p95 processing time per 500 ms RVC input interval. Testing included sustained runs, processing time, memory consumption, startup delay, end-to-end behavior, and failure testing. This figure describes processing time, not end-to-end latency.
